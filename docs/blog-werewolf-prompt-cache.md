# 狼人杀提示词缓存：从 46% 到 83% 的可缓存前缀

> 数据截止：2026-10-26  
> 关键词：狼人杀、Prompt、前缀缓存、上下文工程、降级

狼人杀是最适合观察提示词工程的场景之一：

```text
规则固定
身份固定
公开信息只追加
每轮都有新的发言和行动
```

这意味着它天然适合做“前缀缓存”。

这篇文章讲三件事：

1. 提示词怎么拼。
2. 为什么游戏 ID 在最前、轮次在尾部。
3. 缓存、重试和降级目前做到什么程度。

---

## 一、引擎和 AI 的分工

游戏引擎负责：

```text
角色分配
夜间行动顺序
公开广播
私有信息
投票与放逐
胜负判断
```

AI 只负责当前座位的决策和发言。

角色：

```text
WEREWOLF  狼人
VILLAGER  村民
SEER      预言家
WITCH     女巫
HUNTER    猎人
```

每个角色只看到自己允许知道的信息。

---

## 二、提示词结构

所有 AI 共用固定格式：

```text
[GAME_ID] 对局 ID
[PROMPT_VERSION] werewolf-prompt-v2

【系统提示】
固定规则与隐私边界

【公共广播（按发生顺序追加）】
公开事件

【角色提示】
身份基础提示
当前轮次
私有信息
私有事件
当前存活玩家
当前任务
输出规则
```

用户消息固定：

```text
请执行【当前任务】。
```

### 2.1 公共广播

每条公开事件带：

```text
[seq][R轮次][阶段] 文本
```

例如：

```text
[1][R0][系统] 欢迎来到月白小镇。本局共 6 位玩家。
[4][R1][夜间] 第 1 夜，天黑请闭眼。
```

只追加，不重写。

### 2.2 角色提示

每个身份有一份固定提示，例如狼人：

```text
你的身份是狼人，属于狼人阵营。
夜间你和狼队友共同选择袭击目标；
白天要伪装成好人，制造合理怀疑、带节奏或跟票，
但绝不能承认自己是狼人。
```

具体行动放在【当前任务】：

```text
今晚杀谁
查验谁
是否用解药
是否用毒
投谁
是否开枪
```

这样同一身份不会因为动作不同而产生多套完全不同的系统前缀。

## 三、为什么游戏 ID 在最前面

前缀缓存要求从第一个 token 开始一致。

不同局：

```text
[GAME_ID] 不同
→ 不会复用上一局前缀
→ 每局上下文独立
```

同一局：

```text
[GAME_ID] 相同
【系统提示】相同
【公共广播】只追加
→ 系统 + 早期广播可以持续命中
```

这就是“跨局破坏、局内复用”。

---

## 四、为什么轮次不放在最前面

如果把轮次放在第一行：

```text
[GAME_ID] A
[ROUND] 1
【系统提示】...
```

第二轮变成：

```text
[GAME_ID] A
[ROUND] 2
【系统提示】...
```

从第二个 token 开始就不同：

```text
后面所有 token 都失去相同前缀
→ 整局缓存基本作废
```

所以当前设计是：

```text
[GAME_ID] 在最前
轮次放在角色提示尾部
```

轮次变化只影响尾部，不影响系统提示和公共广播前缀。

---

## 五、广播不裁剪

旧实现有：

```java
if (logs.size() > 260) logs.remove(0);
```

删除最早日志会改动公共广播前缀，导致缓存全部失效。

现在一局游戏保留完整公开广播。

## 六、缓存占比实测

用 6 人局、同一套 builder 做字符级测量：

| 阶段 | 总长度 | 可缓存前缀 | 占比 |
|---|---:|---:|---:|
| 开局 | 666 | 307 | 46.1% |
| 一局结束 | 1862 | 1546 | 83.0% |

开局前缀约一半，随着公共广播追加，比例上升到 80% 以上。

---

## 七、成本下降怎么估算

不同模型供应商缓存价格不同。下面按保守模型估算：

```text
可缓存前缀：50% ～ 83%
缓存命中率：90%
缓存输入价格：正常价格的 10%
```

公式：

```text
有效输入成本
= 非缓存部分
+ 缓存部分 × (命中率 × 缓存价 + 未命中率 × 原价)
```

结果：

| 可缓存前缀 | 估算输入成本下降 |
|---:|---:|
| 50% | 约 40% |
| 65% | 约 53% |
| 83% | 约 67% |

这只是结构估算，不是账单数据。

真正的成本下降要看：

```text
prompt_cache_hit_tokens
prompt_cache_miss_tokens
实际缓存命中率
供应商缓存单价
```

在没有采集 usage 之前，不能把 67% 当成最终账单结论。

## 八、重试和降级

当前狼人杀是：

```text
模型优先
单次调用
失败即规则降级
```

没有应用层重试、没有指数退避、没有熔断。

### 8.1 超时

| 调用 | 超时 |
|---|---:|
| 狼人 / 预言家 / 投票 / 猎人 | 40 秒 |
| 女巫解药 / 毒药 | 35 秒 |
| 发言流 | 45 秒 |
| 每个投票 future | 45 秒 |

### 8.2 规则降级

| 决策 | 降级 |
|---|---|
| 狼人袭击 | 怀疑度 + 随机扰动选好人 |
| 预言家查验 | 查怀疑度最高且未查验的人 |
| 女巫解药 | 首夜救、公开预言家救、否则 35% |
| 女巫毒药 | 第二夜后、已知狼人 75%、高怀疑 32% |
| 投票 | 按怀疑度和公开狼坑补票 |
| 猎人开枪 | 优先公开狼人，否则最高怀疑 |
| 发言 | 本地台词，2 字符/18ms 模拟流式 |

投票的降级最好：

```text
某个 voter 失败
→ 最后对缺失的人 ruleVote 补票
```

### 8.3 仍然存在的缺口

```text
无效目标不一定触发规则补位
半截发言会保留，不回退
投票超时后未取消的 future 仍占线程
没有熔断和降级指标
```

## 九、这套结构解决了什么

```text
公共广播和私有信息分离
角色提示固定
前缀稳定
轮次只改尾部
日志不裁剪
```

结果：

```text
同一局内缓存可以持续命中
不同局不会复用上一局前缀
```

这就是为什么狼人杀的提示词要写成：

```text
游戏 ID 在前
固定系统提示
追加公共广播
角色提示在尾部
```

而不是把所有内容一次性拼成一段。
