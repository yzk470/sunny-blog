# SubAgent 独立验收：让另一个模型判断“真的完成了吗”

> 这是「月白小筑 AI 系统工程笔记」Agent 系列第 3 篇。  
> 关键词：独立验收、产物清单、成功标准、修复回路

## 一、为什么执行者不能自己验收

执行任务的模型有两个天然问题：

```text
它倾向于认为自己做完了
它能看到自己的思考过程，容易自我合理化
```

所以如果让它自己说“完成”，很容易出现：

```text
文件不存在，但回答里写“已生成”
脚本报错，但回答里写“运行成功”
只写了说明，没有真正的产物
```

解决办法不是换一个更强的模型，而是：

```text
让另一个调用只负责验收
```

---

## 二、独立验收能看到什么

`AgentOrchestrator.validate` 是一个单独的模型调用。

它只能看到：

```text
用户任务
成功标准
候选结果
产物目录清单
```

它不能看到：

```text
执行者的思考过程
执行者的工具调用细节
执行者的自我评价
```

输入结构：

```text
用户任务：...
成功标准：...
候选结果：...
产物清单：...
```

输出：

```json
{"passed": true, "reason": "产物存在且符合要求"}
```

或：

```json
{"passed": false, "reason": "缺少 pptx 产物"}
```

---

## 三、验收规则

系统提示里写得很具体：

```text
如果任务要求生成文件（pptx/docx/xlsx/pdf/html/图片等），
产物清单中必须有对应文件。

只有文字说明而没有产物时，不能通过。

如果任务只是要求写脚本并运行，
执行证据中有成功的 run_script/run_command 和真实输出，
且候选结果给出脚本路径与结果，
即使脚本在 workspace 而不在 artifacts，也可以通过。

只有用户明确要求交付脚本文件时，
才要求 artifacts 中有脚本。
```

这条规则很重要：

```text
“交付文件”与“运行脚本”不是同一种任务
```

否则一个只要求“写脚本并运行”的任务，会因为脚本不在 artifacts 里被误判失败。

---

## 四、产物清单从哪来

`AgentArtifactService` 会产出：

```text
文件名
路径
类型
大小
修改时间
URL
```

执行器只拿到清单，不拿到执行过程。

清单本身也是证据：

```text
有没有文件
文件类型对不对
大小是否合理
```

## 五、验收以后发生什么

### 通过

```text
标记 attempt SUCCESS
保存回答
写入记忆
metrics 记录
```

### 不通过

Plan 模式会进入一次修复：

```text
把验收意见写回上下文
→ 重新执行当前步骤
→ 再验收
```

代码里会带：

```text
独立验收意见：
...
```

但修复次数有限，避免无限循环。

### 验收模型不可用

当前实现是：

```java
return new Validation(true, "验收模型暂不可用，跳过二次验收");
```

也就是：

```text
验收失败 → 默认放行
```

这是一个明确的取舍：

```text
宁可跳过验收，也不要因为验收模型挂了把任务全部判失败
```

代价是：

```text
模型故障期间，可能放过不完整的结果
```

这个策略应该在未来改成：

```text
可配置的 fail-open / fail-closed
并把“跳过验收”计入指标
```

## 六、独立验收与普通检查的分工

```text
普通检查：
文件是否存在
格式是否正确
脚本是否有输出

独立验收：
是否真正解决用户问题
是否遗漏关键产物
是否答非所问
```

前者是确定性检查，后者是语义检查。

两者都要有。

---

## 七、独立 rerank Agent

除了验收，还有一个独立子 Agent：

```text
search_knowledge
→ 向量粗检索
→ 独立 rerank Agent 过滤
```

执行者不直接决定哪些知识片段最相关，而是交给一个独立的排序调用。

这和独立验收是同一个思路：

```text
把“判断”从“执行”里拆出来
```

---

## 八、失败分类与修复建议

`AgentFailureService` 会把失败分成不同类别：

```text
TOOL
LOGIC
TIMEOUT
TRANSIENT
UNSAT
```

并给出修复建议，例如：

```text
add_preflight: 先做依赖和路径预检再重试
```

这样下一次 attempt 不是简单重跑，而是带着失败原因重跑。

---

## 九、建设顺序

```text
1. 先有真实产物清单
2. 再做确定性格式检查
3. 再做独立语义验收
4. 再把验收意见接回修复回路
5. 最后做验收失败分类和指标
```

没有真实产物清单，独立验收只能看模型自述，价值很低。

---

## 十、结论

独立验收不是“多调用一次模型”，而是：

```text
换一个视角
只看证据
不看执行者的解释
```

它让 Agent 从：

```text
我说我完成了
```

变成：

```text
另一个角色检查证据后，认为我完成了
```

这是可验收执行的关键一步。
