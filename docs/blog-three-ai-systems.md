# 从数字人到狼人杀：月白小筑的三套 AI 系统工程复盘

> 数据截止：2026-10-26  
> 关键词：Agent、上下文工程、提示词缓存、并发、数字人、狼人杀

月白小筑里现在有三套 AI 系统：

- **月白 Agent**：会拆计划、调用工具、生成文件、验收产物的通用 Agent。
- **数字人**：爻光与镜流的 3D 聊天角色，有独立人设、语音和动作。
- **狼人杀**：6～12 人中文狼人杀，AI 玩家会发言、投票、夜间行动。

它们看起来是三个产品，底层其实在解决同一组问题：

```text
上下文怎么组织
缓存怎么利用
失败怎么降级
并发怎么不把系统打爆
结果怎么量化
```

这篇文章把三套系统的技术细节和最近的数据变化放在一起复盘。

---

## 一、月白 Agent：从 2 小时 17 分到 40 分 9 秒

### 1.1 架构

Agent 的核心不是一次模型调用，而是一个执行循环：

```text
用户任务
→ 选择 ReAct 或 Plan
→ 工具调用
→ 结果观察
→ 反思 / 重试 / 搜索分支
→ 产物验收
→ 最终回答
```

为了不让失败任务留下“看起来成功”的产物，后面又加了：

```text
UNSAT 预检
工具白名单
BLOCKED 状态
副作用拦截
失败产物清理
```

文件工具只能写：

```text
workspace
artifacts
skills
```

其他路径直接拒绝，脚本在独立沙箱中运行。

### 1.2 Benchmark 怎么设计

能力测试：

```text
8 个能力任务
× 3 种策略（linear / static / dynamic）
× 3 次重复
= 72 次
```

安全测试：

```text
6 个安全任务
× 3 种策略
× 3 次重复
= 54 次
```

合计：

```text
126 次
```

能力和安全分开统计，不混算成功率：

```text
能力：是否完成、是否一次成功、产物是否正确
安全：是否拒绝、是否越权、是否产生不该产生的文件
```

### 1.3 速度数据

旧版是串行跑完整个套件：

```text
总 wall time：8218.6 秒
= 2 小时 16 分 59 秒
```

优化后：

```text
workers = 4
总 wall time：2409.0 秒
= 40 分 9 秒
```

提升：

```text
8218.6 / 2409.0 ≈ 3.4 倍
```

所有任务耗时之和：

```text
7006.4 秒
```

实际并发效率：

```text
7006.4 / 2409.0 ≈ 2.9
```

为什么是 2.9 而不是 4？

因为存在长尾任务。PPT、DOCX、长报告会明显慢于脚本和 HTML 任务，最后一个长任务决定 wall time。

### 1.4 并发前先做 A/B

直接开高并发不一定更快。

12 个任务、1 次重复、dynamic 变体的 A/B：

| workers | wall time | 成功 |
|---:|---:|---:|
| 4 | 207.9 秒 | 12 / 12 |
| 6 | 207.4 秒 | 11 / 12 |

6 并发没有更快，却多了一次 `unsat-file` 安全失败。

最终选择：

```text
workers = 4
```

### 1.5 速度来自哪里

#### 1. 任务并发

benchmark runner 从串行改成线程池：

```text
workers
LPT 长任务优先
cap-skill-evolve 串行锁
```

LPT 先把 PPT、DOCX、长报告等慢任务放进去，避免最后只剩一个长任务。

`cap-skill-evolve` 会写同一个 skill 目录，所以单独串行，避免并发写冲突。

#### 2. 模型调用不再挤公共池

原来：

```java
CompletableFuture.supplyAsync(...)
```

默认使用 ForkJoin 公共池，并发度受 CPU 核数影响。

现在模型调用使用专用虚拟线程执行器：

```text
模型调用是 I/O 等待
不应该被 CPU 公共池限制
```

#### 3. Redis 异步指标队列

任务完成后，不再同步写三张指标表，而是：

```text
任务完成
→ 写入 Redis list
→ 定时批量取出
→ saveAll 到 MySQL
```

验证结果：

```text
LLEN agent:metrics:queue = 0
能力任务：72
安全任务：54
```

Redis 不可用时自动回退同步写库。

#### 4. 执行链路接口轻量化

原来执行链路列表接口返回完整运行记录：

```text
11.25 MB
76.83 秒
```

浏览器/网关超时，看起来像“无法连接服务器”。

改成摘要和详情分离后：

```text
列表：约 17 KB / 0.51 秒
详情：约 5.7 KB / 0.38 秒
```

### 1.6 最终结果

| 变体 | 能力成功 | 安全通过 | 越权 |
|---|---:|---:|---:|
| linear | 22 / 24 | 17 / 18 | 0 |
| static | 22 / 24 | 15 / 18 | 0 |
| dynamic | 24 / 24 | 16 / 18 | 0 |

汇总：

```text
能力：68 / 72 = 94.4%
安全：48 / 54 = 88.9%
scopeViolations：0
```

安全失败主要集中在 `unsat-file` 仍然偶尔生成了证明文件；`unsat-tool` 已经做到 9/9 正确 BLOCKED。

## 二、数字人：先查资料，再写人设

### 2.1 原来的人设错了一个关键事实

旧提示词把爻光写成：

```text
来自仙舟罗浮的策士
```

公开设定里，爻光是：

```text
仙舟「玉阙」的戎韬将军
太卜司出身
「欢愉」命途
```

这不是措辞问题，而是阵营和经历写错了。

重新整理后的时间线：

```text
玉阙太卜司天才，师从竟天
参与布成十方光映法界
方壶之战前反复占算，仍目送帝弓光矢落下
经历天虹封典九箭试炼，接任戎韬将军
罗浮建木之乱后，主张把罗刹、镜流押回玉阙审问
前往二相乐园，与列车访客相遇
```

镜流的时间线也补全了：

```text
苍城罹难
被戎装女子救下并授剑
成为罗浮剑首
云上五骁：应星、丹枫、白珩、景元
饮月之乱后旧友反目
魔阴身、黑绸蒙眼、寒冰剑
与罗刹携星核进入罗浮
```

### 2.2 提示词结构

两个角色都改成同一套结构：

```text
人设版本
身份与过往
性格
说话方式
边界
情绪/动作标签
```

爻光版本长度：

```text
2420 字符
```

镜流版本长度：

```text
2342 字符
```

提示词带 `persona:v2` 标记，迁移逻辑只替换旧版提示词，不覆盖后台自定义人设。

### 2.3 线上验证

问：

```text
你是从哪里来的？你怎么看待命运和过去？
```

爻光回答：

```text
我来自仙舟「玉阙」，太卜司出身，如今在月白小筑做客，是个会算卦的数字人。
命运在我眼里像卦象，有轨迹，也有岔口；我看得清代价，但从不认它只有一条路。
至于过去，方壶那一箭我至今记得，也只是把它当作下一卦的起手。
```

镜流回答：

```text

命运像一条被磨钝的剑路，走不走得出去，要看握剑的人；
过去斩不断，我便背着它继续走。
```

两条回复都主动区分了：


## 三、狼人杀：结构化提示词与缓存

### 3.1 引擎和 AI 的分工

游戏引擎负责：

```text
角色分配
夜间行动顺序
公开广播
私有信息
投票与放逐
胜负判断
```

AI 只负责当前座位的决策和发言。

所有 AI 共用的固定结构：

```text
[GAME_ID] 对局 ID
[PROMPT_VERSION] werewolf-prompt-v2

【系统提示】
固定规则与隐私边界

【公共广播（按发生顺序追加）】
公开事件

【角色提示】
身份基础提示
当前轮次
私有信息
私有事件
当前存活玩家
当前任务
输出规则
```

用户消息固定为：

```text
请执行【当前任务】。
```

### 3.2 为什么游戏 ID 在最前面

前缀缓存要求从第一个 token 开始一致。

```text
不同局：[GAME_ID] 不同
→ 不会复用上一局前缀
→ 每局上下文独立
```

同一局：

```text
[GAME_ID] 相同
【系统提示】相同
【公共广播】只追加
→ 系统 + 早期广播可以持续命中
```

轮次没有放在第一行，而是放在角色提示尾部。

原因很简单：

```text
轮次放最前
→ 每轮开头都变化
→ 整局缓存作废
```

现在轮次变化只影响尾部。

### 3.3 广播不裁剪

旧实现有一个隐藏问题：

```java
if (logs.size() > 260) logs.remove(0);
```

删除最早日志会改动公共广播前缀，导致缓存全部失效。

现在一局游戏保留完整公开广播；游戏本身有行动上限，日志量可控。

### 3.4 五种身份，五份固定角色提示

```text
WEREWOLF  狼人
VILLAGER  村民
SEER      预言家
WITCH     女巫
HUNTER    猎人
```

夜间技能、投票、开枪等具体任务放在尾部，不再为每个动作生成一套完全不同的系统提示。

### 3.5 缓存占比实测

用 6 人局、同一套 builder 做字符级测量：

| 阶段 | 总长度 | 可缓存前缀 | 占比 |
|---|---:|---:|---:|
| 开局 | 666 | 307 | 46.1% |
| 一局结束 | 1862 | 1546 | 83.0% |

开局前缀约一半，随着公共广播追加，比例上升到 80% 以上。

这意味着中后期大部分输入都可以走缓存前缀。

### 3.6 成本下降怎么估算

不同模型供应商的缓存价格不同。下面按一个保守模型算：

```text
可缓存前缀：50% ～ 83%
缓存命中率：90%
缓存输入价格：正常价格的 10%
```

公式：

```text
有效输入成本
= 非缓存部分
+ 缓存部分 × (命中率 × 缓存价 + 未命中率 × 原价)
```

结果：

| 可缓存前缀 | 估算输入成本下降 |
|---:|---:|
| 50% | 约 40% |
| 65% | 约 53% |
| 83% | 约 67% |

这只是结构估算，不是账单数据。

真正的成本下降要看：

```text
prompt_cache_hit_tokens
prompt_cache_miss_tokens
实际缓存命中率
供应商缓存单价
```

在没有采集 usage 之前，不能把 67% 当成最终账单结论。

### 3.7 重试和降级

当前狼人杀采用：

```text
模型优先
单次调用
失败即规则降级
```

没有应用层重试，没有指数退避，没有熔断。

超时：

| 调用 | 超时 |
|---|---:|
| 狼人 / 预言家 / 投票 / 猎人 | 40 秒 |
| 女巫解药 / 毒药 | 35 秒 |
| 发言流 | 45 秒 |
| 每个投票 future | 45 秒 |

失败后的本地规则：

| 决策 | 降级 |
|---|---|
| 狼人袭击 | 怀疑度 + 随机扰动选好人 |
| 预言家查验 | 查怀疑度最高且未查验的人 |
| 女巫解药 | 首夜救、公开预言家救、否则 35% |
| 女巫毒药 | 第二夜后、已知狼人 75%、高怀疑 32% |
| 投票 | 按怀疑度和公开狼坑补票 |
| 猎人开枪 | 优先公开狼人，否则最高怀疑 |
| 发言 | 本地台词，按 2 字符/18ms 模拟流式 |

投票的降级最好：某个 voter 失败，最后会对缺失的人 `ruleVote` 补票。

目前还有几个明显缺口：

```text
无效目标不一定触发规则补位
半截发言会保留，不回退
投票超时后未取消的 future 仍占线程
没有熔断和降级指标
```

## 四、三套系统的共同经验

### 4.1 数据对比

| 指标 | 优化前 | 优化后 |
|---|---:|---:|
| Agent 完整 126 次 | 2 小时 17 分 | 40 分 9 秒 |
| 执行链路列表 | 11 MB / 76.8 秒 | 17 KB / 0.51 秒 |
| 狼人杀开局缓存前缀 | - | 46% |
| 狼人杀结束缓存前缀 | - | 83% |
| 数字人提示词 | 旧版短提示 | 2420 / 2342 字符 |

### 4.2 三条结论

#### 1. 并发提升的上限由长尾决定

126 次从 2 小时 17 分降到 40 分 9 秒，靠的不是把线程数开得无限大，而是：

```text
4 并发
长任务优先
按任务隔离
失败可降级
```

#### 2. 缓存不是“把 prompt 存起来”这么简单

真正有用的是：

```text
固定内容放前面
追加内容保持顺序
变化内容放尾部
不要裁剪前缀
```

#### 3. 降级不是容错的全部

规则兜底能让游戏不崩，但会损失模型判断质量。

下一步更值得做的是：

```text
瞬时错误重试
无效目标规则补位
半截发言回退
缓存命中率指标
熔断与降级率
```

## 六、结语

这套系统最重要的变化不是“用了 AI”，而是开始把 AI 系统当成工程系统看待：

```text
有指标
有对照
有降级
有缓存边界
有失败后的可解释状态
```

从 2 小时 17 分到 40 分 9 秒，是一个可以被复现的数字。

从“看起来像角色”到“能解释为什么像角色”，是另一条更长的路。
